# 执行流程与提示词改造评测（2026-11-03）

## 当前结论

本轮完成了执行与验证状态分离、提示词整理、固定任务参考解、重复评测与保守门禁四条工作，并进行了自动化回归和真实模型对照。**P0、P1、P2 分别成功 70 / 72、70 / 72、69 / 72 次；P0→P1、P0→P2、P1→P2 的无退化门禁均为 `insufficient`，不能写成已通过。** 部分任务的成功率下降，当前重复数不足以判断是否为稳定退化。

功能与验证基础设施已经落地，不代表普遍任务能力已经提升；门禁非 `pass` 不能作为能力优化上线通过的依据。因此默认 classpath 提示词恢复为 P0，P2 完整候选保留在 [实验提示词目录](prompt-variants/README.md) 供继续评测，不默认启用。运行时的核验状态与诊断修复继续保留；“新运行时 + P0 提示词”不等于本报告的旧 P0 服务，集成 smoke 也不能代替完整能力对照。

P1 的累计输入 token 比 P0 少 8.03%，但缓存命中率下降 5.76 个百分点，平均耗时增加 10.77%。P2 根据失败轨迹补充两条通用执行规则，并修正诊断中最新核验记录的选择；虽然长文件及 CSV 任务的成功数恢复为 3 / 3，却出现其他失败。金额未观测，不能据此宣称省钱或整体提速。

分类沿用仓库约定：AUTO 为自动化代码或命令验收，MODEL 为接入真实模型运行，MANUAL 为人工或额外环境验证。AUTO 通过不替代 MODEL 结论。24 项是小型 Node fixture，不是大型工业项目能力认证，也不支持“任务百分之百完成”的承诺。

候选提示词没有按模型名称硬编码策略。候选压缩模板保留目标、用户纠正、授权边界、关键证据与版本、未完成任务 ID 和下一步；篇幅是软目标，不能为满足长度删除关键信息。按 Unicode 字符数计算，10 个注册 system 模板从 P0 的 4,230 字符变为 P1 的 2,376、P2 的 2,471；56 个非 README 模型模板合计从 18,830 变为 16,675、16,770。静态字符数不是 token 数，更不能直接证明执行更快或更便宜。

当前工作区另外修复了诊断记录选择：最新的核验结论应覆盖旧核验及旧缺口，后台终态不得被较早记录遮蔽。5 项新诊断测试在原实现中有 4 项失败；修复后与 5 项证据账本测试共同通过 10 项。该修复属于 P2 冻结源码，不能倒算为 P1 已具备的行为。

门禁对每项任务使用单侧 Fisher 精确检验，并按 24 项进行 Bonferroni 校正。`long-file-targeted-edit` 的 3 / 3 → 2 / 3 对应 p 约为 0.5，校正阈值约为 0.00208，未形成显著退化证据；但观察到下降而重复数不足，因此必须返回 `insufficient`。其他任务的进步不能抵消这一待复测项，“没有显著退化证据”也不等于证明无退化。

P0→P2 有 2 项观察下降（`case-insensitive-path`、`add-validation`）；P1→P2 有 3 项观察下降（再加 `path-separator`）。两项对照也均为 `insufficient`，没有达到能力优化上线门槛。P2 是保留的实验候选，不以修好本轮两个失败任务作为启用依据。

失败轨迹复核得到两条通用改进方向：

1. **在约束内寻找可行方案。** P1 长文件任务把格式化器不许变解释为只能停止并请求放宽约束；实际参考解只在允许修改的合计计算处做整数分舍入，即可保持其他格式化函数行为并通过原始测试。问题是没有找完约束内的方案，不能通过放宽测试掩盖。
2. **先最小复现，再归因环境。** CSV 失败答复含有对运行时、加载路径或命令转义的怀疑，其中 P0 答复甚至把环境故障写成已确认原因。现有轨迹不足以支持该归因，应将它作为待验证假设，先复现输入、实际加载的实现与分支行为。P2 为此加入通用规则，不向提示词注入 fixture 专用答案。

P2 的 `case-insensitive-path` 仍暴露真实短板：实现用 `/^\//` 将所有 POSIX 绝对路径都当成根路径提前返回，尾斜杠没有去除；后续调试又重复声明导入变量导致测试语法错误。最终说明将一条实际仍带尾斜杠的输出误述为已去除。通用最小复现提示并不能保证模型正确理解或遵循，必须保留真实输出与外部验收，不能以最终解释替代证据。

三版的两项引导任务共 18 次，均记录实际投递成功；延迟约 1.03–1.05 秒，步数为 0–3。它们验证运行活跃期间的引导接收与本任务最终约束，不能代表已经验证长任务后半程、多次纠正或压缩后的约束保持；尤其 step 0 投递不意味着模型已完成一次代码修改。
