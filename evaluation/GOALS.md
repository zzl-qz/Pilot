# 自适应执行与 Goal

Pilot 把“任务做透”和“跨轮持续运行”分开处理。普通请求不经过独立分类模型，直接由主 Agent 定位、执行、验证并交付；任务复杂但路径明确时仍走普通执行。只有任务必须等待动态结果、依据调查结果反复修复与复验，或用户明确要求持续推进到结果时，主 Agent 才调用 `promote_goal` 激活 Goal，并提交可验证的完成条件。

## 运行协议

- DIRECT（默认）：不增加模式判断或独立审查请求。模型最终答复结束本次执行，任务可进入 COMPLETED 或 AWAITING_REVIEW；这不自动代表验证通过。运行时依据真实证据另记 CHECKS_PASSED（当前版本检查通过）、CHECKS_FAILED（检查失败）、CHECKS_STALE（证据已过期）或 UNVERIFIED（无合格检查）。CHECKS_PASSED 只证明已有检查覆盖的范围，不等于完整目标已核验。普通问答和文档修改没有测试时仍可正常交付；检查失败、陈旧或代码改动无验证时在结果收件箱提示关注，不自动追加模型审查或循环复跑。
- DIRECT 不等于“小任务模式”：路径明确的多文件实现也应在同一次正常执行中做完。运行时没有半预算催交付，也不会因读取或搜索达到固定次数就拒绝继续；重复调用只注入提醒，不再中断运行。
- GOAL：只在候选交付点调用独立核验器。核验器只读任务契约、精简证据账本、候选答复和稳定源码版本，不重复注入整仓库 diff。它可返回 COMPLETE、CONTINUE、WAIT、NEED_INPUT、BLOCKED 或 IMPOSSIBLE；执行模型不能自行宣告 Goal 完成。
- CONTINUE 必须同时给出具体缺口、唯一下一动作和预期观察；计划、搜索、重复摘要和换关键词不重置进展。实际文件状态变化、合格验证、后台终态，以及纯分析任务的新文件阅读或成功获取的网页资料可以重置进展。连续两个核验边界没有新增有效证据时进入 NO_PROGRESS，并保留 Goal。
- WAIT 不要求模型高频轮询后台任务；NEED_INPUT 说明最小解锁条件。核验器返回无效结构时最多重试一次，仍无效进入 VERIFICATION_FAILED；结构可解析但没有可执行下一步时进入 REVIEW_UNAVAILABLE。两者都不能冒充任务失败或成功。
- 外部检索连续失败只禁用当前检索路径，不把整个普通任务判为阻塞。Agent 应改用其他证据或带资料限制交付。
- 收尾先记录计划快照，再运行可选通用完成门（默认关闭），最后进行模式级核验。计划未完成如实上报，不单凭 open step 将正常收尾改判中断或催促继续。Goal 仍须逐项核对用户要求；全部核验通过时同步收口陈旧的内部计划。

## 证据与版本

每条工具证据记录 SUCCESS、EMPTY、TRANSIENT_FAILURE、PERMANENT_FAILURE、DENIED、RUNNING、CANCELLED 或 SKIPPED，以及执行前后版本。完成证据只接受 SUCCESS。源码版本只哈希本任务实际写过的文件，使用完整文件流计算；界面展示截断、超过 64 KiB 的 diff、无关脏文件和之后读取的新路径都不会改变旧证据。后台命令的结果绑定启动时版本，源码变化后旧测试不能验证新版本。

验证命令先分类为 TEST、BUILD、STATIC_ANALYSIS、FORMAT_CHECK 或 OTHER；前四类且最终成功退出才属于合格检查，是否仍适用还取决于源码版本与相关性；它们不自动证明用户的所有要求均已满足。`git status`、`git diff`、`node --version`、`cargo metadata` 等环境检查即使退出码为 0 也只是普通观察。续跑从任务记录恢复改动路径和合格检查，避免上一执行段的修改在新段里被误当成“没有改代码”。

同步 `spawn_agent` 在构造时冻结工具快照并移除派生、调度和 Goal 控制工具；单次子运行最多使用 8 个工作步和 1 个收尾请求（合计最多 9 次模型请求），同一 run 共享最多 4 次派生、24 次子模型请求的资源池。子请求、活跃时间和 token 用量计入父任务的事故熔断，不能借派生绕过任务预算。子工具通过结构化结果把全部 `changed_files` 和 `checks` 合并到父循环与证据账本，失败或触顶时也保留已经产生的事实，父 Agent 仍必须完成最终核对。

## 资源与停止

累计记录主执行、Goal 核验与阶段收尾的请求数、主动耗时、输入 token、输出 token 与推理 token。预算是高位事故熔断，不是任务规模分类器或日常完成条件：DIRECT 每段默认 120 个主执行请求、2 小时、800 万输入和 50 万输出；Goal 使用 `pilot.agent.max-steps` 个主执行请求（默认 120）、4 小时、800 万输入和 50 万输出。核验器在主额度之外最多预留 2 次请求。步数触顶且计划未完成时，沿用计划进展与次数上限进行自动续跑；用户也可主动继续开启同模式的新预算段。累计用量、停滞计数、证据、缺口、唯一下一动作和预期观察不清零；任务记录保存预算段编号。

静态工具的相同调用只有实际结果也相同时才计入停滞：达到配置的提醒次数后软纠偏，不按相同调用次数硬停止；结果变化会重置计数，不提前跳过可能产生新观察的调用。`command_status` / `command_logs` 使用更宽的有界观察窗口，长期完全不变才暂停。输出 `finish_reason=length` 会按剩余工作续写，连续三次才停止。

上下文预算先本地清理旧工具输出和截断超长观察，再尝试摘要；摘要阶段默认完整保留最近 5 组 action/observation，只有真正超窗的硬裁剪才允许降到 2 组。摘要连续 3 次没有收益，或成功摘要后连续 3 次快速回填，会熔断摘要模型调用；熔断期间仍执行本地裁剪，使用率真正降到低水位后才恢复。

取消之外的所有停止都会预留一次禁用工具的收尾请求；预算停止使用专门的 wind-down 合同，保存已满足条件、改动文件、验证、缺口与恢复动作。收尾模型不可用时使用确定性兜底文字。运行结束状态与任务结果状态分离：WAITING、NEED_INPUT、UNVERIFIED、NO_PROGRESS、REVIEW_UNAVAILABLE、VERIFICATION_FAILED、BLOCKED 和 BUDGET_LIMITED 都可继续，但不会伪装成完成。

## 恢复与并发

任务 ID、原始目标、约束、纠正、完成条件、证据、已改路径、Goal 缺口、下一动作、预期观察、预算段和资源用量持久化到任务记录。用户纠正通过要求版本检查使旧核验失效，但保留已经发生的文件改动供重新验证；暂停、重启、检查点和分支沿用同一契约。续跑还会从历史恢复只读任务已经检查过的路径和工具数量，内部续跑/停滞提示只在下一次采样的 system runtime context 中出现，不写成用户消息或持久会话。

队列只在运行和人工验收都完成后交接。后台命令独立运行；执行模型使用有界状态查询观察结果变化，进入 WAITING 后暂停模型请求，等后续继续时再观察外部状态，不靠无限高频轮询。

## 验证

`GoalExecutionPolicyTest` 覆盖 Direct 无额外分类或审查请求、执行与核验状态分离、失败与陈旧检查、显式 Goal 升级及无进展止损、稳定大文件指纹、无关文件不失效、后台旧结果、结构化子代理结果、类型化验证、检索路径降级、核验器故障、真实 token 预算和旧数据迁移。

`AgentLoopTest` 覆盖 finish reason、输出截断恢复、静态重复与动态轮询、临时 runtime guidance、上下文压缩熔断、步数保险丝和所有停止路径的无工具收尾。`AgentRunTaskControlTest` 覆盖 Goal 缺口续跑、持久证据恢复、核验失败、陈旧计划收口、用户纠正、暂停、队列与人工验收。前端事件测试覆盖各阶段结果的独立可恢复展示。

真实模型评估使用固定任务、可解参考实现与独立验收，记录模型/提示词/工具版本、调用量、token、继续原因、工具轨迹和最终状态；界面、附件与跨端行为另做实际交互验收。普通任务不应因提示词调整增加固定分类请求；复杂任务的质量收益和成本变化须由重复对照运行证明，失败时保留阶段交付。单元测试、fixture 验证和 dry-run 均不能替代真实模型能力结论。
