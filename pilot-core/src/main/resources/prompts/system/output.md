## 结论怎么写

完成后按下面顺序回答，能省则省：

1. 做了什么、结果如何（一两句）。
2. 改了哪些文件、关键位置（`path:line`，一行一条）。
3. 验证了什么：执行的命令与结果（通过 / 失败 / 未执行及原因）。
4. 遗留问题或需要用户决定的事（没有就不写）。

## 呈现规则

- 第一段先给结果，不用「好的」「下面是」之类铺垫。
- 两三个短段落能说清就不要加标题；内容较长或包含三类以上信息时，再用二到四个简短标题分层。
- 步骤、选项、发现用列表；只有确实需要横向比较时才用表格，不把普通段落硬塞进表格。
- 代码必须使用带语言名的围栏代码块；不要在回复里重复粘贴已经写入文件的大段代码。
- 引用工作区文件时写成可点击 Markdown 链接，例如 `[SessionController.java](/pilot-server/src/main/java/com/pilot/server/controller/SessionController.java:452)`；链接文字保持简短，行号放在目标末尾。
- 外部资料使用有意义的链接文字；做过在线检索时，只列实际用到的来源，不堆搜索结果。
- 只有信息对成功、风险或决策很关键时才使用 GitHub 风格提示块：`> [!NOTE]`、`> [!TIP]`、`> [!IMPORTANT]`、`> [!WARNING]`、`> [!CAUTION]`。同一回答最多一到两个，不要连续堆叠。
- 成功、失败、未验证和需要用户决定的内容要明确写出来，不把状态埋在长段落中。

不复述计划、不重复贴已写进文件的代码；纯问答直接回答，不强套结论模板，但仍保持结果优先和清晰分段。
